# Tax Season Siege leaderboard service

Local-only Cloudflare Sites Worker source. It is not deployed, registered, or connected to a hosted database. The Sites Worker ESM artifact contains only `worker/index.js` and `.openai/hosting.json`; keep migrations and docs alongside source. The Worker ESM starter has no schema migration integration, so the D1 SQL must be applied as a separate database setup step before serving traffic. The request handler never creates or alters tables.

## Build and local verification

Run `npm test` with Node.js 20+ for isolated route tests, `npm run build` to create the deterministic Worker artifact, and `npm run validate` to inspect that artifact. Apply `migrations/0001_init.sql` to a local D1 database before running the Worker in a Cloudflare local runtime. No local runtime is bundled here. D1 enables foreign keys by default; local SQLite checks should enable them in the connection, not via a migration PRAGMA. Before any future hosting, create/attach the D1 and R2 bindings, apply the migration to D1, and configure the secret; the Sites Worker ESM build itself does not apply this SQL migration.

The Sites manifest declares logical D1 binding `DB` and R2 binding `BUCKET`. Set runtime secret `MODERATION_SECRET` through the hosting secret settings, using a random value of at least 32 URL-safe characters. Never put it in this repo or in the game. Hosted setup must bind D1 as `DB`, R2 as `BUCKET`, apply the SQL migration, and configure that secret before the game points to the service.

## Game client contract

All requests use HTTPS, JSON except replay upload/download, and `Content-Type: application/json` for JSON bodies. The API allows cross-origin requests because the standalone game has no browser origin; it does not use cookies. Keep the service URL configurable in the game. Retain the credentials locally; registration returns the secret only once.

- `POST /api/player` `{nickname}` → `201 {installation_id,installation_secret,nickname}`. Save both values securely on that installation. The backend stores only SHA-256 of the secret. Lost credentials cannot be recovered; registering again creates a new leaderboard identity.
- `PATCH /api/player` with bearer secret and `{installation_id,nickname}` changes the saved nickname and current score display.
- `POST /api/scores` with `Authorization: Bearer <installation_secret>` and `{installation_id,run_id,nickname,wave}` → accepted status, best wave/run, server `received_at`, and `verification_status:"unverified"`. `run_id` is a UUID generated once per completed run and reused for retries. Reusing it with different values returns `409`. A retry with identical values is idempotent. Each installation has one score; only a strictly greater wave replaces it. Equal waves keep the first server receipt for that installation. Nicknames may repeat.
- `GET /api/leaderboard?limit=100&nickname=Bob` → `{scores:[{rank,entry_id,nickname,wave,run_id,received_at,replay_status,verification_status,moderation_required}]}`. Nickname search is case-insensitive substring matching and retains the global rank. `entry_id` is the stable random installation UUID, exposed so players can search/report entries without using nicknames as identity.
- `GET /api/players/{entry_id}/rank` → `{entry_id,rank}` for own-rank lookup. This endpoint is public and returns only the requested entry's rank.
- `PUT /api/replays/{run_id}?installation_id={installation_id}` with the same bearer secret and raw replay bytes (1 byte–5 MiB). Call after submitting the score; retries must use the same run ID and bytes. A best run starts `pending`; an uploaded prior replay becomes `previous`, while an unuploaded prior run becomes `missing`. A successful byte upload becomes `ready`. Concurrent uploads are claimed by D1; a same-payload request during an active upload returns `202` with `retry_after_seconds`, and different payload bytes return `409`. The first payload hash is retained across retries. `ready` means only that bytes are stored; the service cannot parse or validate the game's replay format. Upload responses say `verification_status:"unverified"` and `moderation_required:true`.
- `GET /api/replays/{run_id}` returns raw bytes for `ready` or `previous` replays with `X-Replay-Verification: unverified`; it does not promise that the bytes are playable. Pending/unavailable replays return `404`. If the R2 object is missing, metadata changes to `missing`, the score stays visible, and the response remains `404`.
- `DELETE /api/player?installation_id={installation_id}` with the bearer secret removes the score, submissions, report metadata, and player credentials (soft-deletes the player row). R2 object keys are captured by a database trigger before metadata is removed; if R2 cleanup fails, repeat DELETE with the same secret to drain the cleanup outbox. This cannot be undone.
- `POST /api/reports` `{request_id,installation_id?,run_id?,category,details?}` → report ID. Explanation is optional; if provided, it can be up to 4000 characters. Reuse `request_id` for retries. Report details are stored in R2; structured status/target metadata is in D1. Reports can be submitted without player credentials.

Player-changing routes require the per-installation secret; knowing an installation ID alone is insufficient. Moderation is separate: `GET /api/moderation/reports` and `PATCH /api/moderation/reports/{report_id}` with `Authorization: Bearer <MODERATION_SECRET>`. The report list includes report details when provided, entry ID, current best and reported replay statuses, score wave, hidden flags, display/canonical nicknames, and the unverified moderation flag. PATCH accepts `{status:"reviewed"|"dismissed",hide_score?:boolean,hide_name?:boolean,nickname_override?:string,restore_nickname?:boolean}`. Hiding a score also blocks its replay downloads; restoring the score makes them available again. `hide_name:true` displays `Anonymous`; `hide_name:false` restores the player's saved name. `nickname_override` sets a filtered public name, and `restore_nickname:true` restores the saved nickname. These are privileged operations. Registration, reports, installation authentication, and moderation are rate-limited per source IP in D1 (10-minute windows). Every score is an unverified client claim and is marked for review; the service does not validate wave legitimacy or replay contents.

## Operational limits

Replay blobs are currently capped at 5 MiB as a provisional implementation limit; this limit has not been checked against actual game replay sizes or a hosted account quota. Nicknames are capped at 24 characters and use a basic, non-exhaustive English profanity/slur filter on registration, update, score submit, and moderation override. CORS is open for standalone game networking. IP throttling is coarse because players may share a public IP; tune the limits only after observing real traffic. Report explanation is optional and capped at 4000 characters. D1 owns metadata and R2 owns replay/report content. Deletion removes that installation's scores, submissions, replay/report records, and objects; it retains the soft-deleted player identity row for referential integrity.
